# Stage 3 full-universe persistence verification

**Finding:** BUG-STAGE3-PERSIST-PARAM-LIMIT, from the independent audit and reproduced here.

**Fix:** commit `037a17f`, "fix(stage3): make feature persistence parameter-safe".

**Evidence:** `audit/evidence/stage3_persistence_full_universe.json`. It was generated on 2026-09-28 at 15:18 UTC by `backend/ops/measure/stage3_persistence_verify.py --session 2026-09-28`, which is committed.

## Where it ran

- **No production write.**
  - The snapshots were **computed** from the production database `prajna` using the dry-run path: REPEATABLE READ, READ ONLY.
  - The rows were **persisted** by the production code (`engine.consistent_read` + `engine.persist`) into the test database `prajna_test`.
- **The target was an isolated schema**, `stage3_verify_2396614`, not a separate database: the role `prajna_rw` has no CREATEDB privilege.
  - `feature_value` and `ingest_run` were replicated from prajna_test's public schema, with the same constraint names, CHECK constraints, indexes and append-only trigger. The 25 DDL statements are listed in the JSON.
  - The unique constraint is `uq_feature_value (instrument_key, session_date, snapshot, feature_id, feature_version)`.
  - The CHECKs include `ck_feature_pit` and `ck_feature_value_or_reason`.
  - The trigger is `tr_feature_value_append_only`.
- Real **COMMIT**s were made there. The schema was then dropped (`schema_dropped: true`).
- `prajna_test.public.feature_value` held 0 rows before and 0 after.

## 1. Before

| Item | Result |
|---|---|
| Code | `persist()` inserted `values[i:i+5000]` per statement |
| Parameters per row | **15**, counted from the compiled statement (`pg_insert(FeatureValue).values(...).compile(asyncpg)`): 1 row = 15, 2 rows = 30, 5,000 rows = **75,000**. `feature_value` has 16 columns; `id` is generated by the server |
| Limit | asyncpg allows 32,767 parameters per statement |
| Experiment | The real PRE_SESSION snapshot of 2026-09-28 (3,547 instruments, 180,919 rows), persisted into prajna_test inside a rolled-back transaction |
| Observed | `sqlalchemy.exc.InterfaceError: (asyncpg...InterfaceError) the number of query arguments cannot exceed 32767`. Nothing was written. A production run would have failed the same way, after compute, as a FAILED run |
| Why the tests missed it | The seed world persists at most about 275 rows, which is about 4,125 parameters in one statement |

## 2. Change

The batch size is now derived from a parameter budget: `PARAM_BUDGET = 30000`, about 8% under 32,767.

- `batch_rows(params_per_row) = PARAM_BUDGET // params_per_row`, which gives 2,000 rows (30,000 parameters) at 15 per row.
- `params_per_row` is taken from the row's keys, which is exactly what the statement binds (see the regression test).

## 4. Atomicity, idempotency, determinism, rollback

| Step | Experiment | Observed |
|---|---|---|
| A | PRE_SESSION persisted in one REPEATABLE READ transaction. A **second connection** counted the rows before COMMIT | 0 visible before COMMIT; 180,919 after. Inserted 180,919 |
| B | The same rows persisted again (a rerun) | inserted 0, already present 180,919, count unchanged |
| C | A **second, independent compute** from production (140.2 s), persisted | inserted 0, already present 180,919. The recompute agrees with every stored value (determinism on real data) |
| D | One value changed (`NSE_EQ\|IN9175A01010:ret_1d`, −0.0144 → 0.9712) | `DeterminismMismatch: 1 stored feature values differ from a recompute; nothing overwritten`. Rolled back; the stored value is still −0.0143992055611; 180,919 rows |
| E | PRE_OPEN with a failure **injected after its first INSERT batch** had executed | `InjectedFailure: injected after INSERT batch 1`. Rolled back; **0 PRE_OPEN rows remain** |
| F | PRE_OPEN persisted | 0 visible before COMMIT; 195,107 after; 98 statements |

## 5. Regression tests (`backend/tests/stage3/test_engine.py::TestPersistScale`)

| Test | Proves |
|---|---|
| `test_bind_parameters_per_row_are_counted_from_the_real_statement` | 1 row = 15 parameters. `batch_rows(15)` rows = 30,000 ≤ budget < 32,767. One more row exceeds the budget. 5,000 rows = 75,000 > 32,767 |
| `test_rows_across_several_batches_persist_then_rerun_is_idempotent` | 5,000 rows go in 3 statements of 30,000 / 30,000 / 15,000 parameters, captured at the driver. The rerun inserts 0. No duplicate keys. A changed value raises DeterminismMismatch and overwrites nothing |
| `test_a_failure_after_a_batch_leaves_no_partial_snapshot` | through `run_snapshot`: a failure after the first INSERT batch leaves 0 feature values and 1 RUN_FAILED |

With the old `step = 5000` restored, the two database tests fail with `the number of query arguments cannot exceed 32767`. With the fix, they pass.
